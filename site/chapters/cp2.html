Checkpoint 2: Crash-Safe WAL Ledger

Repair a write-ahead log replay double-credit bug, strengthen the ledger invariant, and prove conservation across arbitrary crash loops.

Checkpoint Bug · Crash Between Balance Update and ACK 
structure WalLedger where
  balance   : Nat
  appliedTx : List Nat -- committed tx IDs persisted in WAL
-- Buggy recovery re-runs `balance := balance + tx.amount` without checking `tx.id ∈ appliedTx`!
-- After 1 crash-restart, a $500 deposit credits $1,000.
Socratic Gate · Commit to a Prediction Unanswered · Locks on commit

After adding the deduplication guard `if txId ∈ s.appliedTx then s else ...`, what inductive invariant links `s.appliedTx` to replaying `txId` after `k` crashes?

Why this happens:

Crash-Recovery Verification Pattern

Storage engines, Kafka consumers, and Stripe-style payment ledgers achieve effectively-once state updates over at-least-once delivery by persisting transaction IDs inside the same atomic WAL batch as the balance mutation. Proving idempotence + monotonic appliedTx membership guarantees zero double-credits across arbitrary crash-restart traces.
